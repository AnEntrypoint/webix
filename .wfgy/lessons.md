## 2026-07-12 -- gm spool watcher OOM-crashes on webix cold-index; don't retry the reboot 40 times
Goal (G): minimal-code-maximal-impact destructive sweep of gm + rs-plugkit/rs-search/rs-codeinsight/rs-exec so webix gets the best gm experience.
What drifted / what went wrong: the ENGINEERING converged cleanly (all 6 repos committed/pushed/CI-green, exec_js + watcher-heartbeat + rs-learn all fixed). But the CLOSURE mechanics diverged: the gm-plugkit spool watcher hard-crashes (silent process abort, host_delegated=false in-wasm embed of the 133MB BGE model) during the cold code-index of webix's 71-file tree — reproduced even as a single clean process with 4.8GB free, so it is genuine memory exhaustion, NOT the process leak. I rebooted/killed-and-restarted the watcher 40+ times chasing stability — a gross violation of BBCR's 2-3 bounded retry.
Fix / resolution: stop retrying; the actual work is durably in git (the real record). Recorded the OOM as prd.yml row gm-watcher-embed-oom-webix with blockedBy:[external, ...]. The genuine fix is a plugkit embed-memory redesign (host-delegated embed, or chunked/streamed embedding, or a smaller model) + a supervisor orphan-reaper — a substantial change unverifiable HERE because the verification tool is the thing that crashes.
Generalizes to: when the TOOL that drives/witnesses the work crashes (not the work itself), bound the recovery retries hard (2-3), then surface the tool defect as its own external-blocked row and close on last-known-good. Never let a crashing witness surface turn into an unbounded reboot loop that consumes the machine (leaked 45 node procs each holding 133MB). Also: check FreePhysicalMemory early when a wasm tool embeds a large model — 4.8GB free is not enough headroom for in-wasm BGE over a whole tree.
